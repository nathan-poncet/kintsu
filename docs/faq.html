FAQ

Twenty-four questions in five groups. Missing one? Open an issue.

Safety and privacy

Does Kintsu ever run a command?

No. Never. A fix is inserted in your line editor; you press Enter. In the panel it takes two Enters on purpose: one to insert, one to run. Rules can be marked auto by you, one by one, never by default. The only thing that runs on its own is a read-only probe attached to a rule, such as lsof -i :3000 for a port in use, and only when you ask Why; the Privacy tab lists it.

What exactly is sent, and when?

Nothing until you pick an action that needs a model. Then the redacted case: the command line, exit status and duration, the captured output, the working directory, the git branch and whether it is dirty, the last ten commands with their statuses, and the project hints Kintsu found (a package manifest, a CLAUDE.md). Never environment variables, never file contents, never your history beyond those ten lines. The Privacy tab shows the exact payload before and after.

What if there is a secret in the output?

Redaction runs before anything is sent and is on by default: API keys, bearer tokens, JWTs, passwords in URLs, private keys, plus your own patterns. When it finds one, the case is marked sensitive and the router refuses every cloud candidate for it: the answer comes from a local model or from rules alone. kintsu privacy shows the redacted token as sk-live-••••.

Can I use it fully offline?

Yes. Rules need nothing. With Ollama, classification, fixes and explanations run on your machine; set offline = "local_only" or simply configure no cloud model. Without Ollama you keep the rules and the hand-off to a CLI agent, and Kintsu prints once a day which models are missing.

Does it keep logs? Telemetry?

No telemetry, no account, no server of ours, ever. Locally, Kintsu keeps small files under ~/.local/state/kintsu: the last commands of each shell, the last failure, the ignore list. Cases are stored as typed, like your shell history; secrets are redacted before anything is sent to a model or an agent, and kintsu privacy shows exactly what would leave. Delete the directory and it is gone.

Can a web page with a kintsu:// link do something to my shell?

No. A click can only open or focus the panel on an action; it can never insert a command, run one, or start an agent. Case ids are random 128-bit tokens that expire with the case, the socket is a local Unix socket with the peer's uid checked, and there is no network listener.

Compatibility

Which shells?

zsh, bash and fish, on Linux and macOS. zsh and fish support ghost-text fixes and messages that arrive while you type. bash has no preexec and no safe way to draw while readline waits, so messages come at the next prompt and there is no ghost text; everything else is the same. PowerShell and nushell are planned later.

Which terminals make the bubble clickable?

Any terminal that renders OSC 8 hyperlinks: iTerm2, WezTerm, Kitty, Ghostty, foot, VS Code, Windows Terminal, GNOME Terminal and the other VTE terminals. Alacritty through its hints. Terminal.app does not render links, so the words show but do not click; the keys and the commands still work. The panel uses real mouse tracking while it is open, everywhere.

Does it work over SSH, inside tmux, inside Herdr?

Yes. The daemon runs per user on whatever host the shell is on, so on a server it runs on the server. In tmux and Herdr, Kintsu reads the output with capture-pane and pane read; WezTerm, Kitty and iTerm2 expose their scrollback through their APIs. Elsewhere the case is the command and its status until you enable the opt-in stderr capture.

Will it slow down my prompt?

On success, the hook assigns a variable and returns: under a millisecond, no process. On failure, the client queries the daemon with a 40 ms budget and prints the toast if a rule answered in time; otherwise it returns and the bubble arrives later. The synchronous path makes no network call. If the daemon is not running, the hook prints nothing.

Does it change my exit status or my history?

No. The hooks return the status of your command so your prompt and your $? are untouched, and they never write to your history. The dependency tests and the hook tests in the repository check both.

Models and cost

What does an answer cost?

Rules and the tiny local model: nothing. An explanation from a small cloud model such as Haiku: about a tenth of a cent for a typical case. A large model: a few cents. Your agent: whatever your subscription already covers. A daily cap, max_daily_cost, is planned.

Can I use my Claude, ChatGPT or Copilot subscription instead of an API key?

Yes, through the CLI you already have: Claude Code, Codex, Copilot CLI or Gemini CLI configured as a cli_agent. Kintsu writes the brief and launches the CLI; the CLI uses its own login. That is how Agent works, and it can also serve Why and Fix if you route them there, at the cost of a slower answer.

Do I need Ollama?

No, but it makes a noticeable difference. With a tiny local model, classification and summaries are free and instant, and sensitive cases still get an answer. Without it, those tasks fall back to rules and the toast is generated from rules only. Add it under [models] with provider = "ollama".

How does the router pick a model?

Per task, an ordered list of candidates from your config. The router drops what the constraints forbid (a cloud model for a sensitive case, a paid model past the budget, a slow model for a fast task), skips a model after three consecutive failures (circuit breaker), and takes the first one left. On a timeout it moves to the next. The last candidate is always rules-only.

Which providers?

Anthropic, OpenAI, Gemini, Ollama, and any endpoint implementing the OpenAI chat API: OpenRouter, Groq, Mistral, Together, LM Studio, llama-server, vLLM. Plus any CLI agent as a provider. Keys come from your keychain, an environment variable or a command such as op read; a literal in the file works and gets a warning.

Compared to

Isn't this Warp?

Warp did it first, and did it well, inside Warp: with a Warp account, Warp's models and Warp's quota. Kintsu does it in the terminal and shell you already use, with any model or agent, keys in your keychain and the source on GitHub. If Warp suits you, keep it.

Isn't this thefuck?

For chapter 1, yes, and Kintsu ports its best rules with credit. thefuck waits for you to type a word, has no model for what rules cannot know, cannot read the output, and cannot hand a case to an agent. It also starts a Python interpreter each time; Kintsu's fast path is a native binary.

Isn't this Claude Code, Codex, Copilot CLI, Gemini CLI?

Those are agents you start yourself. Kintsu detects the failure, writes the brief and launches them with the case attached. They are not competitors; they are where Agent hands off to.

What about zsh-autofix, ai-fix, butterfish, shell_gpt?

Each covers part of it: zsh-autofix triggers on failure but is zsh plus oh-my-zsh plus Ollama only; ai-fix re-runs your failed command to capture its error, which is unsafe; butterfish wraps your shell in a PTY; shell_gpt and aichat are chat CLIs you call. None combines the automatic trigger, any shell and terminal, any model, safe capture and a real hand-off. The full comparison is in the vision document.

The project

What works today?

The hooks, and a placeholder line after a failure. The bubble, the daemon, the rules and the models are designed in four documents and come with v0.1. The roadmap shows what becomes real when, chapter by chapter.

Why Rust, and why one binary?

The fast path runs after every failed command and must start in well under a millisecond; a static binary installs everywhere, including a server you do not own. One crate, three rings as folders, a test that enforces the dependency rule. It is an application, not a library.

License, contributions?

MIT. Issues and pull requests are welcome; the most useful contribution before v0.1 is an opinion on the design documents. Conventions are in CONTRIBUTING.md.

Why "Kintsu"?

Kintsugi, 金継ぎ, is the Japanese craft of repairing broken pottery with gold. The name says what the tool does: it repairs failed commands, visibly.
